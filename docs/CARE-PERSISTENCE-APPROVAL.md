## Why this design

**Exact SQL revision for the renewed approval:** SHA-256 `42b332cf5d6ce22483c28669115149ddf76014c809a1be0af17b055b1f3973a7`. This replaces the earlier proposal that would have granted new reads to the existing reader. It creates a separate Care reader instead, so rollback does not require revoking/changing original authorization. Actual dedicated-test original-reader authority/evidence guards and purchase reads still pass after the additive SQL; that reader is denied access to the new tables.

Care needs durable state so a return timeline, warranty date or watch survives reloads and background checks. Keeping that state separate from purchase/payment evidence prevents a manual report or model answer from becoming a verified financial fact. One bounded database-only checker is simpler and safer than an always-running AI agent per product. The current merchant/goods are fictional: this creates working persistence/checking, not invented carrier connectivity or real warranty coverage.

The approved Care UI can read current records and prepare drafts without new authority. Durable manual return milestones, warranty terms and saved/active watches cross a separate boundary. Exact approved SQL is [care-persistence.sql](proposals/care-persistence.sql). Its DDL is now registered in the selected **`drizzle/care`** lane and checked byte-for-byte after removing only comments/transaction envelopes; Drizzle provides the atomic transaction and inserts into its existing migration journal. The unchanged root migration lane is never run for application Care activation, so deferred 0016 is not applied.

## Pause, disable and rollback

1. **Pause one/all watches:** the private worker command supports `pause WATCH_UUID` or explicit `pause all`. `resume` changes operational state only and does not reset the recorded daily due time, expiry or source. Dedicated-DB tests prove paused watches are skipped, resume does not force an early repeat check, and expiry stops checks.
2. **Disable every background check:** stop/disable the new timer and its oneshot service. No existing app or financial service is stopped. No real worker is installed/enabled yet.
3. **Application rollback:** stop the candidate, restore the retained verified application assets/configuration on the same private 8444 → 3002 route, and run actual readiness/HTTPS smoke. The original reader has no new grants, so its original startup policy remains compatible. The old launcher ignores the new Care-only configuration; it still uses current legitimate credentials/accounting.
4. **Database rollback is deliberately non-destructive:** retain the three additive tables and append-only records, leave the new paths disabled, and keep original tables/grants unchanged. No DOWN migration drops history or restores a stale database backup. A later cleanup/removal would be separately approved, not automatic rollback.
5. Verify purchase/document/event fingerprints, original credential hashes and current accounting before/after. Existing unknown requests and reservations are never released or restored from snapshots. Actual application-migration rollback rehearsal remains a release prerequisite; isolated schema/role tests do not claim it occurred.
