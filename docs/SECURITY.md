# Security and privacy design

**Subsequent exact owner activation approval:** 300 total inference requests, four simultaneous, 30/rolling-minute and at most one safe pre-stream admission retry, customer chat/personal Insights only. Atomic reservations cover every attempt, including retries; uncertain/cancelled/partial responses never retry. Refresh alone is serialized; owner revocation remains independent. Actual provider/HTTPS acceptance is recorded in STATUS/handoff, not assumed from configuration. Earlier disabled-delivery statements below retain their original scope. Paid credits are owner-attested off (not machine-inspectable); no API/financial fallback exists.

**Persistent private-owner implementation (live inference disabled):** [current architecture/threat model](PERSISTENT-OWNER-AI.md) supersedes the request-only/four-hour HTTPS operating procedure below. New protected storage is separate from historical files; browser authentication and immutable standing policy/accounting are distinct. Exact Host/Origin, Secure/HttpOnly/Strict `__Host-` cookies, hashed secrets, browser-agent binding, absolute/idle expiry and revocation apply. All provider calls recheck policy/quota/permission before refresh and durable dispatch; unknown usage is not refunded. No policy/allowance or real provider refresh is activated. Same-agent cookie theft, same-host ports, owner/root/Docker access and in-flight requests remain explicit limitations. Historical checks below retain their original scope.

**Testing access request preparation:** the private HTTPS page may display its existing non-secret window state and copy a bounded proposal into the clipboard. Neither requesting nor copying proves ownership or grants/renews anything. No write endpoint, queue, credential field, remembered-owner bypass or automatic provider refresh is added. Exact owner verification/limits/HTTPS pairing remain required before future activation. [Current request-only scope](TESTING-ACCESS.md).

**Current private HTTPS presentation:** owner-approved Serve **8444 → 127.0.0.1:3002**, exact `https://greatbison.tail9e8802.ts.net:8444`, no wildcard hosts/forwarded-header authority or Funnel. Native private-development presentation grants no AI/owner/financial capability. HTTPS explicitly disables evaluation/pairing, preserves the old deadline for read-only display and does not migrate localhost grants. Original evaluation/owner checks remain unchanged. Cookies are host-scoped, **not port-isolated** from other services on the same hostname; no Domain widening is added. Tailnet ACLs/device sharing govern reachability, not model/financial permissions. [Current evidence](evidence/TAILSCALE-ACCESS.md).

**Owner-approved private persistence:** `palcare-preview.service` keeps only the loopback website available after the original AI window ends. Its allowlisted runtime preserves subscription mode and denies missing/expired authority; no fixture AI, renewal, owner pairing, paid fallback or financial operation is enabled. Only private website readiness is decoupled; all model/scope/session/accounting guards remain authoritative. Actual database roles/evidence guards still gate startup and readiness. The Mac launchd tunnel uses strict existing SSH trust/batch authentication and loopback binding, not a public service or an authentication bypass. Same-user/Docker/root and local-forwarding risks remain; persistence does not establish public isolation. [Evidence and limitations](evidence/PRIVATE-PREVIEW-PERSISTENCE.md).

## Sensitive assets

Sensitive assets include database URLs, PayPal app credentials/OAuth tokens, anonymous checkout capabilities and selected sandbox transaction references. Product/customer data is fictional and public. No real customer data is allowed. Raw provider responses and payer identity are never persisted or logged.

### Implemented checkout safeguards (actual Sandbox happy path verified; not production certification)

- 256-bit HttpOnly/SameSite=Lax browser cookie; Secure on HTTPS. Only SHA-256 token digests are stored. A checkout UUID/return token is not authorization.
- Exact Origin checks, JSON-only 2 KiB request bodies, UUID/product allowlists; no visitor-supplied amount/currency/merchant parameters.
- PostgreSQL counters: 3 new orders/session/hour, 10 globally/hour, 30 globally/day. Provider operations additionally have per-order/global hourly/daily limits. No IP addresses are retained.
- Persisted create/capture UUIDs, a two-hour create deadline and durable concurrent-operation leases. Capture intent is saved before dispatch; ambiguous captures only reconcile. An operator must investigate unresolved attempts, not reset their markers or invent completion.
- The same-origin, cookie-bound `reconcile` action requires an already-attempted payment, accepts no visitor capture ID and cannot create/capture at PayPal. Existing capture identity is pinned from validated order evidence and independently retrieved through Payments v2. Expiry does not disable attempted-capture reconciliation. Status observations alone do not authorize a verified Twin; pending, failed, declined, mismatched or incomplete evidence cannot fabricate completion.
- Retrieve and validate both order and capture: status, amount/currency, merchant, item SKU/quantity, application references, final-capture flag and timestamps. Atomic Twin/document/event insertion and unique provider references prevent duplicate records.
- Original product/policy/callback/payee context is snapshotted. Raw SDK payload logging is not enabled; sanitized error status/debug IDs are the only provider diagnostics.
- An optional immediate-test scope is server-only: one request UUID/session digest, fixed SKU/USD 129.00 price and an initially false balance-confirmation flag. New creation is blocked before insertion/provider calls while unconfirmed and rejected for a different scope. Neither the browser nor a URL can set funding preference or confirmation. The preference is persisted only on the new order; old nulls preserve original SDK bodies and financial keys. Balance selection remains a buyer-confirmed PayPal UI step, never payment proof.
- No runtime mock-provider or arbitrary provider-base-URL switch. Tests inject doubles into the service or intercept browser transport only. Production SDK environment is hardcoded Sandbox.
- Webhooks are absent; signature verification/delivery has not been tested. See `docs/PAYPAL.md` before claiming live integration.
- `docs/PAYPAL-WEBHOOKS.md` assesses a future public-HTTPS listener, verification, inbox and retry/deduplication boundary. It adds no current webhook route or delivery claim.

### CareOS boundary (private subscription acceptance; API/public gates remain)

Approved subscription mode adds CareOS's own official OAuth connection, not a proxy to OpenCode/Codex. Expiring customer/Studio scopes and conversation cookies gate local model access. Credentials stay in protected host files, never the browser/Git/runtime environment; browser artifacts and deployment traces are checked. Actual terminal SSE output was empty, so completed item identities/final phases are reconstructed before strict output validation. Care instructions render selected approved-source wording rather than unverified model prose. No schema/financial permission is expanded.

Private access status is read-only and private/no-store: only window state, expiry and independently validated scope booleans reach the UI. It cannot issue/extend cookies, renew approval or consume/refund usage. Existing persistent scope cookies remain HttpOnly/SameSite=Strict/host-only/Secure on HTTPS and expire at approval's deadline. Missing/deleted cookies require explicit authorization after legitimate renewal, normally through the owner pairing below; no longer-lived automatic login is added. Loopback does not mean owner-only OS access: local processes, authorized SSH forwarding, the same Unix identity and root/container administrators remain relevant. Cookies are not port-isolated. [Actual network/host observations and limits](evidence/PRIVATE-ACCESS.md).

The approved private launcher additionally enables explicit **SSH-authorized browser pairing**, replacing manual scope-token transfer in normal owner use. A pending public request ID alone has no authority: completion requires a 256-bit HttpOnly browser secret (only its hash is stored), five-minute/window-bound host approval for the exact requested scopes and exact Origin. Only a host CLI under existing protected-file ownership can approve; no HTTP approval or inference/financial tool exists. Grants are single-use, atomically consumed before cookie issuance, and tied to the original session approval, window, origin and scope hashes. Persistent caps bound issuance without touching inference budgets. Original scope cookies/deadline and all protected endpoint checks remain unchanged. This is not independent owner identity proof beyond the existing owner SSH/OS account: compromised owner/root/SSH access, malicious same-host processes and phishing an owner into approving somebody else's request remain threats. Approve only the request displayed in your own browser. No long-lived owner bypass or public deployment is introduced.

Subscription requests use a separate durable host allowance (initially 30, owner-raised to 50 total with original attempts/expiry retained), serial dispatch, no SDK retries and preserved unknown slots. Additional paid credits remain owner-confirmed off; this setting cannot be machine-inspected here. No API fallback or API-dollar accounting is used for subscription calls. Studio failures persist terminal unavailable results/release leases without refunding quota. Existing 0015 conversation persistence remains; 0016/API budgets below are separate. CareOS adds bounded conversation writes, not purchase/merchant authority. A separate 256-bit HttpOnly capability (digest only in PostgreSQL), exact Origin, strict 16 KiB JSON/2,000-character message schemas, session/global quotas, single-turn leases and persisted request fingerprints protect its endpoints. Public visitors cannot supply trusted history, tools, identities, provider URLs, prices or payment actions. Responses and transcript reads are private/no-store. Knowledge is product/brand/model filtered, hash-checked and treated as untrusted text.

The focused UX keeps one bounded, 24-hour per-tab pending-question hint in session storage for reload recovery, never credentials or trusted history. It validates the hint, keeps the original request envelope and reads saved results without automatically replaying POSTs. A missing result remains uncertain and never releases provider usage. Dated purchase choices are server-derived, explicitly confirmed and reauthorized on the new scoped turn; older selectors are inactive. Appearance, reading-space and keyboard geometry are presentation only and make no model/financial request. [UX evidence and limitations](evidence/CAREOS-UX.md).

The paid Responses adapter has no tools, automatic retries, arbitrary URLs or financial privileges. Strict output, source/quote checks and escaped components constrain output; none eliminates prompt injection or proves truth. API activation requires approved credentials/budgets. **API-dollar** per-call reservations settle independently; identical settlement is idempotent, changed usage fails, unknown calls retain their full reservation, and observed overruns persist a spending block. Original API budget buckets are retained across UTC boundaries. Clear/cleanup never replenishes API budgets or the separate subscription allowance. `store:false` is not a zero-retention guarantee. Expired content is inaccessible after 24 hours; private cleanup removes it physically. Simple receipt requests load no unrelated recall/knowledge/Guardian evidence. Relevant unavailable evidence never becomes a fabricated all-clear. See [CareOS](CAREOS.md).

1. **Authorization:** public reads expose fictional records only; future consequential operations must verify operator authority and exact merchant/record/action scope and limits on the server.
2. **Secret isolation:** only trusted server processes access database/provider secrets. Never commit `.env`, tokens or sandbox passwords. Use separate migration credentials and a least-privilege runtime database role before expanding to write workflows.
3. **Payment integrity:** use integer minor currency units, trusted PayPal captures and verified authorization and remaining refundable amount.
4. **Safe retries:** durable payment operation IDs, concurrency-safe reservations, no duplicate refunds after timeouts.
5. **Webhook authenticity:** validate PayPal webhook signatures and accept each provider event once.
6. **Documents:** current sample documents are public. Personal uploads are out of scope. Before adding private documents, explicitly design authorization, storage, validation and deletion.
7. **Prompt-injection resistance:** treat uploaded files and third-party text as untrusted content; AI output cannot change security policy.
8. **Truthful states:** requested, processing, completed and failed are distinct; completion depends on authoritative provider confirmation.
9. **Auditability:** append state changes with actor and source references, without unnecessarily storing or logging sensitive documents.
10. **Regression checks:** invalid ownership, cancelled checkout, simultaneous refund requests, webhook replays, unexpected policy versions and provider failures.

## Scope disclaimer

All protected runtime capabilities use the shared inspection policy with distinct allowed operations. A privileged login narrowed with `SET ROLE`, or a NOINHERIT login that can assume an unsafe role, is rejected. Dedicated-test verification uses actual temporary restricted logins and forbidden direct-write tests. It creates no application/provider account or actual transaction. Readiness performs only bounded local checks; optional remote-provider outages are not a reason to make paid health calls or restart the entire application.

Pal Care does not independently underwrite warranties, issue insurance, decide PayPal Purchase Protection eligibility, or guarantee merchant price-match terms.
