## Engineering boundaries

Customer Intelligence is the approved primary analytics direction: **Home / Purchases / Insights / Documents**, `/insights`, and its **My Purchases / Documents & Care / Price Adjustments** views. Existing merchant analytics is retained secondary context, not the customer's core journey. Native Studio grid/chart/KPI and custom evidence widgets must share actual scoped data/cross-filters and validated layouts; a custom-card-only or merchant-only demonstration does not accept this scope.

CareOS must execute real Studio Agent Framework tools and verify **exact SDK postconditions**: selected page, filter/cross-filter field/operator/value, widget identity/type/data mappings/aggregation, selection/layout, and resulting visible purchase IDs/counts/amounts. Adding a widget is idempotent; reset/restore must match the declared state; empty or failed outcomes must not be reported successful. Model intent, emitted events or `success` strings alone do not prove execution. [Detailed acceptance contract](CUSTOMER-FIRST-PLAN.md#exact-sdk-postconditions-required-for-b).

Earlier private CareOS/merchant-Studio acceptance is retained with its failures/limits; the new customer path now has its own **5/5 actual Sol/SDK** evidence. Further useful real Sol Medium calls require the existing actually unexpired session and remaining journal allowance, checked before dispatch; retain prior usage/unknowns and stop on expiry/exhaustion/denial. No new allowance, session reset/renewal, identity rotation, paid credits or API fallback is authorized. Bounded private scenarios do not establish public access/licensing, owner approval or population accuracy.

- Refund execution must be authorized server-side, never delegated directly to AI or a dashboard agent.
- PayPal purchase and refund evidence must come from actual Sandbox responses, not a mocked state.
- Price-change replay must be clearly labeled as a controlled test scenario while exercising real application domain rules; it is not production certification.
- A recall candidate must cite an official source and support confirming the product model before asserting it is affected.
- Channel3 cards must use real returned product identity and approved outgoing retailer links.
- Recorded dashboard figures derive from stored records. Explicit illustrative scenarios remain separate and never imply actual business outcomes or enter financial tables.
- Customer charts/KPIs describe the loaded saved-purchase window, not universal history/lifetime spending. Sample and verified Sandbox records stay labeled; reference zero placeholders remain unavailable prices; adjustment totals require independently verified recorded refund evidence for the exact Twin. Missing evidence is not zero or an all-clear.
- Missing external API data must fail gracefully with an appropriate timestamp and source label.
- One genuinely retrieved historical CPSC notice is limited coverage, not comprehensive continuous monitoring. Channel3's fixture/injected-transport evidence is not a real provider call; **actual returned product records are still required**.
- Reuse restricted runtime roles, immutable snapshots/financial evidence and original 0015 records/schema. Engineering does not authorize paid calls, application migrations/credential changes, financial actions, license/trial activation or deployment. Private model approval does not relax public visitor/model-spending scope controls.

## Sponsor matrix and award limits

The award limit is **up to one Grand Prize OR one Honorable Mention, plus up to one Sponsor Prize**. Multiple integrations can be considered, but do not stack Grand + Honorable Mention or multiple sponsor awards in projected outcomes. Sponsor tools are optional for the overall competition; central meaningful PayPal + AI is required.
